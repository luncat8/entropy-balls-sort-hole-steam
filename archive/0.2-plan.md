# 0.2 — Sorting objectives and progression

## Outcome

Each participant has an independently generated objective: change the composition of one chamber and meet the objective either immediately or for a continuous interval. The initial game has one participant; the task interface supports more without assuming a global current task.

## Design

- `tasks.js` owns objective definitions, generation, evaluation and lifecycle, keyed by stable participant id. It reads only `simDist` (per-side totals, per-palette counts, hot/cold counts, revision), never `simBalls`. `simulation.js` fills that snapshot at the end of every fixed step from ball centers (`x < wallX` is left). Participant creation and control ownership belong to `players.js`.
- A task specifies side, category (`hot`, `cold`, or one named palette color), strict comparator (`>` or `<`), threshold and completion mode (`immediate` or `hold`). Randomly choose either mode at generation; a hold requires two continuous simulation seconds. Show the mode and hold progress in the task view.
- The percentage is matching balls on the chosen side divided by all balls on that side, based on center position. An empty side has no percentage and never satisfies either operator. Display the numerator and denominator so the meaning is clear.
- Evaluate once per fixed step. An immediate task completes on the first satisfying step. For a hold task, elapsed time is `steps * dt` while satisfied (not a summed accumulator); reset it when false or the side is empty. Complete once at two seconds, replace only that participant's task, and evaluate the replacement no earlier than the next step.
- Balls retain immutable hot/cold and color metadata. Use the six-color palette from 0.1, with three colors per temperature category. Temperature is a label, not a physical property.
- Generate from bounded candidate thresholds (`30, 40, 50, 60, 70`) and categories using an injectable random source. Compare with integers: `match * 100 ? threshold * sideTotal` so `1/2` is neither `>50` nor `<50`. Feasibility is side-independent (any nonempty split of the live population); only the already-satisfied check reads the named chamber. Reject a task if no nonempty split could meet it or if it is already satisfied when assigned. Account for discrete counts, strict comparisons, and absent categories. One pass over the shuffled candidate space — if none survive, show a waiting state and retry only when `simDist.rev` changes. New ball generation may later change feasibility.
- Keep per-participant task and hold state separate; share the evaluator and generator. Evaluate at the end of `simStep` so catch-up still samples every fixed dt; a replacement is not evaluated until the next step.
- The UI receives a read-only view model. `tasks.js` paints a compact `#task-strip` from that model so the objective is visible in this slice. `status.js` remains gui.1. The second participant and bots are not required in play; the APIs still accept two participant ids.

## Files and ownership

- `simulation.js` — `simDist` snapshot filled after each fixed step.
- New `tasks.js` — task rules, generation, per-participant lifecycle, and the task strip.
- New `players.js` — participant identity, type and lifecycle; initialize one human participant.
- `index.html` — `#task-strip` and script order (`players.js`, `tasks.js` before `main.js`).
- `main.js` — boot and wiring only. Update the `AGENTS.md` ownership map.

## Validation

- L0: `node --check` on touched JavaScript.
- L1: test side denominator, strict thresholds, empty sides, immediate and continuous-hold completion/reset, replacement timing, absent categories and discrete feasibility, bounded waiting/retry, and independent state for two participant ids.
- Manual: arrange distributions, check displayed counts and both completion modes, and verify a successor appears once.
